# Architecture

This document distinguishes implemented components, historical test-system evidence and remaining validation. The intended system boundaries are unchanged. The ordinary `src/server.ts` starts the HTTP application with `/health`; it does not automatically connect SQLite, SumUp checkout creation or verification, the payment webhook, or Poster submission. Separate sandbox scripts can perform external requests when explicitly authorized.

## Layers

1. **Communication channels** — adapters will translate messages from the selected pilot channel into a common internal format and send replies back. Instagram, WhatsApp, Facebook and Telegram are not connected yet.
2. **Order core** — menu snapshots, carts, deterministic totals in integer EUR cents, pickup, delivery addresses with an explicitly supplied fee, and order-state transitions are implemented. Customer records, modifiers, delivery rules and delivery time remain future work. Language models must not supply authoritative prices or availability. The `submitted_to_poster` domain transition does not itself submit an order.
3. **Database** — file-backed SQLite stores the local order-to-SumUp-payment link and one durable Poster handoff marker per order. The marker includes a stable local correlation ID and SHA-256 fingerprint of the exact built payload. A versioned schema enforces unique order, checkout, checkout-reference, successful-transaction, correlation and Poster-order identities; the repository atomically commits the verified `paid` transition for order/payment and the completed Poster transition for order/handoff. A claim written before the injected Poster submitter provides at-most-once protection across connections and process restarts: completed claims return `duplicate`, unresolved claims return `in_progress` or `uncertain` and are never automatically resent. A read-only inspection exposes `not_started`, locally `confirmed`, or `unknown` together with durable identity. A read-only mode opens an existing database without migrations and rejects mutations. The schema allows one payment per order; a complete payment retry lifecycle is not implemented. Channel identities, conversations, delivery progress and the wider event journal remain future storage work.
4. **Payment provider** — SumUp merchant reads, Hosted Checkout preparation/creation, a transport-neutral webhook contract, application service and optional Fastify route are implemented. `SumUpSandboxCheckoutVerifier` reads the checkout and its linked successful transaction using authenticated HTTP requests, validates identity, merchant, EUR and amounts, then returns normalized reconciliation data. Successful verification uses two GET requests without retry; early failure can use fewer. The route returns an empty `204` after successful processing, `400` for a contract error and `503` for processing/verification errors. Customer messages and webhook bodies alone never count as proof of payment. The actual HTTP verifier requires `PAID` and `SUCCESSFUL`: non-paid checkouts raise an error, although the local service/repository support non-paid results supplied by an injected verifier. Thus the real sandbox route does not currently persist `failed`/`expired` from this verifier.
5. **Poster** — the read-only adapter reads account settings, menu identifiers and per-spot prices; the menu-check script compares the returned account with configuration. It can also return opaque rows from the historically used read-only `incomingOrders.getOwnIncomingOrders` method, but does not guess their field mapping. A pure payload builder and dry-run support a paid pickup order with exactly one product line and include prepayment fields. A local application service accepts only a locally confirmed `paid` order, uses that builder and calls an injected submitter behind a stable interface. The sandbox-only submitter uses the confirmed `incomingOrders.createIncomingOrder` endpoint, requires its stable local correlation ID in the existing comment field, permits one attempt per instance and converts network, HTTP or ambiguous-response outcomes to `uncertain` without retry. Repeated calls reuse a completed result only for the same correlation ID and payload fingerprint; another identity is blocked as `uncertain` without POST. Its token-aware HTTP transport owns no configuration lookup and is disabled unless constructed with an injected token and `enabled: true`; neither it nor the inspector is wired into the ordinary server. A separate recovery service can call only an injected read-only inspector: `unknown` keeps the order `paid` and persists `uncertain`; only a `confirmed` result matching order ID, correlation ID and payload fingerprint may atomically complete the handoff. The sandbox inspector strictly compares normalized Poster order ID, an explicitly expected status, venue, EUR amount, the sole product, quantity, price, payment type, prepayment and synthetic contact/reference fields. The bridge over the existing client requires an injected raw-response decoder because those current Poster fields have not yet been freshly confirmed. Local tests use fake transports, fetchers and decoders; no real request occurs in the ordinary server or tests, and no production account is connected. Local correlation metadata alone is not external proof.
6. **Event journal** — sandbox webhook observability emits restricted diagnostic events. A complete persistent append-only journal for order, payment, integration and handoff events remains future work and must avoid card data and unnecessary personal data.

## Separate sandbox and recovery tools

The E2E harness starts a separate loopback webhook server with SQLite and the HTTP verifier after a merchant preflight. Separate commands create one checkout per guarded local attempt, inspect local status, replay a duplicate for an already paid pair, verify an existing checkout read-only, and clean up recovery files. None is started by the ordinary server bootstrap.

Recovery locators and SQLite are retained for incomplete attempts, with the hosted checkout URL stored separately in the ignored private recovery directory. Automatic cleanup is gated on the duplicate helper's paid-pair, empty `204` and unchanged timestamp/transaction checks; explicit cleanup is a separate command. This lifecycle cannot recreate artifacts already deleted from an older attempt.

The recovery verification CLI reads existing state and SQLite without marking the order paid. It permits at most two external GET requests and requires both for success. It supplies sandbox/EUR metadata locally rather than reading the stored merchant preflight or performing a new Get Merchant request; it therefore does not independently re-establish sandbox identity. Successful recovery verification would prove neither webhook delivery nor local reconciliation.

## Historical evidence and remaining validation

- Test Poster settings/menu reads and one successful minimal incoming-order POST are recorded in `docs/CHANGELOG.md` and commit `0cbd407`. The successful POST omitted prepayment, explicit price, name and comment. It does not validate the current prepaid payload builder, the wider field mapping or kitchen visibility. The cause of the earlier `422` remains unknown.
- SumUp sandbox merchant access and Hosted Checkout creation were recorded in `c905bb3`, `6d1fb1d` and `204b5b6`. In the last recorded E2E attempt, the user reported completing the Test mode page, but no webhook was recorded and local order/payment remained unpaid. No authenticated checkout/transaction verification established successful payment. The cause of missing delivery remains unknown; that attempt's temporary artifacts were deleted.
- Local tests cover domain rules, mocked HTTP responses, the injected webhook flow, real temporary SQLite, and recovery helpers. They are not a successful external E2E test. The corrected verifier and recovery tools have not been validated against a successful external sandbox payment in the recorded evidence.
- Server-verified payment, provider webhook delivery, real sandbox `paid` and duplicate, recovery of the deleted attempt, the current Poster incoming-order read schema, Poster prepayment, kitchen visibility and the full end-to-end scenario remain unconfirmed. The project is not ready for a pilot. Historical access checks do not establish current credential validity.

The existing ChoiceQR website remains separate from this application. ChoiceQR is paused as an integration option; any return to scope requires an explicit user decision. SumUp remains the first payment candidate, with any alternative requiring a separate decision. External adapters should depend on stable interfaces exposed by the order core so that channel, payment and POS concerns do not leak into domain rules.
