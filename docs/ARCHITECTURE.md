# Architecture

This document distinguishes implemented components, historical test-system evidence and remaining validation. The system now includes a provider-neutral AI orchestration boundary and a provider-specific OpenAI adapter between communication adapters and the deterministic conversation/order core; no real provider transport or production wiring is connected. The ordinary `src/server.ts` starts the HTTP application with `/health`; it does not automatically connect SQLite, SumUp checkout creation or verification, the payment webhook, Poster submission, or the AI layer. Separate sandbox scripts can perform external requests when explicitly authorized.

## Layers

1. **Communication channels** — adapters will translate messages from the selected pilot channel into a common internal format and send replies back. Instagram, WhatsApp, Facebook and Telegram are not connected yet.
2. **AI orchestration** — an injected provider-neutral interpreter receives only channel/user identity, conversation phase, cart item IDs/quantities, fulfilment choice, presence flags for required customer fields and checkout existence. It returns either a strictly validated existing `ConversationAgentCommand` or a bounded clarification result. Unknown command types, extra fields, prices, totals, availability, delivery fees, payment/order statuses and Poster fields are rejected. For an existing conversation, identity and processed-message fingerprints are checked before the interpreter: a matching duplicate returns its stored deterministic command/result, while mismatched identity or source text is rejected without a provider call. The application service delegates new accepted commands to `LocalConversationAgentService`; it has no order, payment, checkout, Poster or network dependency. No channel adapter or real provider transport is connected.
3. **OpenAI adapter** — `OpenAIConversationInterpreter` implements the provider-neutral port. It reads `OpenAIConfig` with a local `OPENAI_API_KEY`, defaults to model `gpt-5.6-luna` and reasoning effort `high`, sends only the safe context and client text through an injected transport, and validates model JSON through the existing runtime allowlist. Its Responses-shaped request always sets `store: false`; its strict JSON schema requires every declared field, represents unused values as `null`, disables additional properties at every object node, and is checked recursively by a local contract validator. Malformed, unknown or authoritative fields become bounded clarification; no HTTP transport, API call or ordinary-server wiring is provided by this stage.
4. **Order core** — menu snapshots, carts, deterministic totals in integer EUR cents, pickup, delivery addresses with an explicitly supplied fee, and order-state transitions are implemented. Customer records, modifiers, delivery rules and delivery time remain future work. Language models must not supply authoritative prices or availability. The `submitted_to_poster` domain transition does not itself submit an order.
5. **Database** — file-backed SQLite stores the local order-to-SumUp-payment link, one durable Poster handoff marker per order and the transport-neutral conversation state. The versioned conversation migration persists conversation/channel/user identity, its unique order and checkout references, cart, customer/fulfilment fields, safe payment/submission snapshots, processed message history with the last message ID, and timestamps. New AI-created processed-message records also retain the canonical command/result and a SHA-256 fingerprint of normalized source text, never the raw message, so AI duplicates remain deterministic after SQLite reopen; the decoder remains compatible with older records that lack these optional fields. Create/update uses parameterized SQL inside `BEGIN IMMEDIATE`; immutable identity, checkout and processed-message history plus database uniqueness constraints prevent cross-conversation reassignment and repeated message effects across process restarts. It stores no card data, provider secrets, or raw webhook/provider responses. The Poster marker includes a stable local correlation ID and SHA-256 fingerprint of the exact built payload. The schema enforces unique order, checkout, checkout-reference, successful-transaction, correlation and Poster-order identities; the repository atomically commits the verified `paid` transition for order/payment and the completed Poster transition for order/handoff. A claim written before the injected Poster submitter provides at-most-once protection across connections and process restarts: completed claims return `duplicate`, unresolved claims return `in_progress` or `uncertain` and are never automatically resent. A read-only inspection exposes `not_started`, locally `confirmed`, or `unknown` together with durable identity. Repository read-only modes open an existing database without migrations and reject mutations. The schema allows one payment per order; a complete payment retry lifecycle is not implemented. Delivery progress and the wider event journal remain future storage work.
6. **Payment provider** — SumUp merchant reads, Hosted Checkout preparation/creation, a transport-neutral webhook contract, application service and optional Fastify route are implemented. `SumUpSandboxCheckoutVerifier` reads the checkout and its linked successful transaction using authenticated HTTP requests, validates identity, merchant, EUR and amounts, then returns normalized reconciliation data. Successful verification uses two GET requests without retry; early failure can use fewer. The route returns an empty `204` after successful processing, `400` for a contract error and `503` for processing/verification errors. Customer messages and webhook bodies alone never count as proof of payment. The actual HTTP verifier requires `PAID` and `SUCCESSFUL`: non-paid checkouts raise an error, although the local service/repository support non-paid results supplied by an injected verifier. Thus the real sandbox route does not currently persist `failed`/`expired` from this verifier.
7. **Poster** — the read-only adapter reads account settings, menu identifiers and per-spot prices; the menu-check script compares the returned account with configuration. It can also return opaque rows from the historically used read-only `incomingOrders.getOwnIncomingOrders` method, but does not guess their field mapping. Pure builders and dry-runs support both the current prepaid pickup payload and the historically successful diagnostic minimum containing only spot, synthetic phone and one product ID/count. The minimal profile deliberately omits price, payment, names and comment without changing the default prepaid handoff. A local application service accepts only a locally confirmed `paid` order together with its linked `paid` SumUp record. The standard builder independently requires a non-empty verified transaction and checkout reference, matching order ID, exact order/payment total and EUR before emitting `payment: { type: 1, sum: <integer cents>, currency: "EUR" }`; it rejects missing, pending or mismatched payments before the injected submitter can run. The sandbox-only submitter uses the confirmed `incomingOrders.createIncomingOrder` endpoint, permits one attempt per instance and converts network, HTTP or ambiguous-response outcomes to `uncertain` without retry. Its standard handoff shape requires the stable local correlation ID in comment; the exact minimal diagnostic shape is also accepted but carries no external correlation field. Repeated calls reuse a completed result only for the same correlation ID and payload fingerprint; another identity is blocked as `uncertain` without POST. Its token-aware HTTP transport owns no configuration lookup and is disabled unless constructed with an injected token and `enabled: true`; neither it nor the inspector is wired into the ordinary server. A separate recovery service can call only an injected read-only inspector: `unknown` keeps the order `paid` and persists `uncertain`; only a `confirmed` result matching order ID, correlation ID and payload fingerprint may atomically complete the handoff. The sandbox inspector strictly compares normalized Poster order ID, an explicitly expected status, venue, EUR amount, the sole product, quantity, price, payment type, prepayment and synthetic contact/reference fields. The bridge over the existing client requires an injected raw-response decoder because those current Poster fields have not yet been freshly confirmed. A successful minimal POST could be inspected only from its returned `incoming_order_id`; timeout or an ambiguous response cannot be recovered safely by correlation while comment is omitted. Local tests use fake transports, fetchers and decoders; no real request occurs in the ordinary server or tests, and no production account is connected. Local correlation metadata alone is not external proof.
8. **Event journal** — sandbox webhook observability emits restricted diagnostic events. A complete persistent append-only journal for order, payment, integration and handoff events remains future work and must avoid card data and unnecessary personal data.

## Separate sandbox and recovery tools

The E2E harness starts a separate loopback webhook server with SQLite and the HTTP verifier after a merchant preflight. Separate commands create one checkout per guarded local attempt, inspect local status, replay a duplicate for an already paid pair, verify an existing checkout read-only, and clean up recovery files. None is started by the ordinary server bootstrap.

Recovery locators and SQLite are retained for incomplete attempts, with the hosted checkout URL stored separately in the ignored private recovery directory. Automatic cleanup is gated on the duplicate helper's paid-pair, empty `204` and unchanged timestamp/transaction checks; explicit cleanup is a separate command. This lifecycle cannot recreate artifacts already deleted from an older attempt.

The recovery verification CLI reads existing state and SQLite without marking the order paid. It permits at most two external GET requests and requires both for success. It supplies sandbox/EUR metadata locally rather than reading the stored merchant preflight or performing a new Get Merchant request; it therefore does not independently re-establish sandbox identity. Successful recovery verification would prove neither webhook delivery nor local reconciliation.

## Historical evidence and remaining validation

- Test Poster settings/menu reads and one successful minimal incoming-order POST are recorded in `docs/CHANGELOG.md` and commit `0cbd407`. The successful POST omitted prepayment, explicit price, name and comment. It does not validate the current prepaid payload builder, the wider field mapping or kitchen visibility. The cause of the earlier `422` remains unknown.
- SumUp sandbox merchant access and Hosted Checkout creation were recorded in `c905bb3`, `6d1fb1d` and `204b5b6`. After an earlier incomplete attempt, one later 100-cent sandbox flow recorded a real webhook, authenticated server-side verification, checkout `PAID`, exactly one matching `SUCCESSFUL` transaction, atomic local `paid`, and one duplicate replay without additional verification or state mutation. This is historical evidence, not confirmation of a new current run or current credential validity.
- Local tests cover domain rules, mocked HTTP responses, the injected webhook flow, real temporary SQLite, and recovery helpers. They remain synthetic evidence and do not replace a fresh external E2E validation before a pilot.
- The current Poster incoming-order read schema, durable preservation of prepayment and all mapped fields, kitchen visibility and the full end-to-end scenario through Poster remain unconfirmed. The project is not ready for a pilot. The cause of the earlier missing SumUp delivery remains historical and unknown; that attempt's temporary artifacts were deleted.

The existing ChoiceQR website remains separate from this application. ChoiceQR is paused as an integration option; any return to scope requires an explicit user decision. SumUp remains the first payment candidate, with any alternative requiring a separate decision. External adapters should depend on stable interfaces exposed by the order core so that channel, payment and POS concerns do not leak into domain rules.
