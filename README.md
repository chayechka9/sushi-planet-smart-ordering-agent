# Sushi Planet Smart Ordering Agent

## Цель проекта

Создать умного агента для Sushi Planet, который принимает заказы из социальных сетей, помогает клиенту выбрать блюда, принимает оплату и передаёт оплаченный заказ в Poster, где его видят сотрудники и кухня.

Основной сценарий:

```text
Instagram / WhatsApp / Facebook / Telegram
→ наш агент
→ корзина и итоговая сумма
→ оплата
→ подтверждение оплаты
→ оплаченный заказ в Poster
→ кухня и доставка
→ сообщение клиенту со статусом
```

## Исходные сведения о ресторане

Эти сведения зафиксированы ранее; они не означают, что интеграции агента уже
реализованы или что доступы и состояние внешних систем проверены заново.

- Ресторан: Sushi Planet, Dublin.
- Существующий сайт: [Sushi Planet](https://sushiplanet.ie/delivery/section:menu).
- Сайт работает через ChoiceQR.
- Онлайн-оплата на сайте проходит через Adyen.
- POS-система ресторана: Poster.
- Для разработки создан отдельный тестовый Poster-аккаунт
  `sushi-planet-bot.joinposter.com`. Это не аккаунт Sushi Planet и не
  production-среда ресторана.
- Заказы с сайта автоматически появляются в Poster.
- В Poster передаются данные клиента, телефон, блюда, сумма, комментарий, адрес и время доставки.
- Заказы из социальных сетей сейчас заносятся в Poster вручную.
- Instagram, Facebook и WhatsApp Business связаны в одном Meta Business-аккаунте.
- ChoiceQR используется для сайта и заказов с сайта.
- Poster является основной рабочей системой для заказов, кухни и доставки.

## Текущее состояние проекта

### Реализовано в коде

- Основа Fastify/TypeScript, health route, корзина, расчёты в евроцентах,
  самовывоз, адрес и явно заданная стоимость доставки, переходы статусов.
- SQLite order/payment persistence: сохранение связанной пары, атомарный
  переход в `paid` после проверки данных платежа и защита от повторной
  обработки, в том числе после повторного открытия базы; durable Poster
  handoff marker блокирует повторную отправку после claim или перезапуска.
  AI-created conversation history хранит fingerprint нормализованного
  исходного текста, но не raw message, вместе с безопасно декодируемой командой
  и результатом.
- SumUp Hosted Checkout builder/client, HTTP-verifier checkout и transaction,
  локальный webhook-flow, отдельные sandbox E2E/recovery-инструменты.
- Read-only Poster client, prepaid и минимальный диагностический payload/dry-run,
  paid-only handoff с injected submitter, sandbox-only one-shot transport и
  read-only inspector boundary. Эти Poster-компоненты не подключены к обычному
  серверу; raw incoming-order decoder и production transport отсутствуют.
- Provider-neutral AI orchestration boundary: injected interpreter получает
  ограниченный контекст и возвращает только allowlisted command либо
  clarification; известные identity mismatch, duplicate и message conflict
  разрешаются по SQLite state до interpreter, а новые команды передаются
  существующему deterministic conversation core. Локальный OpenAI HTTP
  transport реализован, но обычный runtime, `server.ts` и каналы к нему не
  подключены.
- Provider-specific OpenAI adapter реализует этот interpreter через injected
  client/transport; `OPENAI_API_KEY` читается только локальной конфигурацией,
  defaults — `gpt-5.6-luna` и reasoning `high`. Strict schema требует все
  поля, использует nullable значения для неактуальных аргументов и проходит
  рекурсивный локальный contract check; request всегда задаёт `store: false`.
  Responses API transport отправляет этот request одним `POST` с ограниченным
  timeout и без retry, принимает API key только для Bearer header и возвращает
  безопасные ошибки без provider body. Transport и adapter не подключены к
  обычному `server.ts`; реальный OpenAI runtime не запускался.

Обычный `server.ts` запускает только приложение с health route: он не включает
SQLite, checkout/verifier, webhook или AI layer автоматически. Sandbox-инструменты
запускаются отдельно. Локальные тесты с mock-ответами и временной SQLite
проверяют компоненты, но не доказывают работу внешнего сквозного сценария.

### Исторически проверено в тестовых системах

- В отдельном тестовом Poster прочитаны настройки и меню; успешный минимальный
  POST создал один входящий заказ. Предоплата, явная цена, имя и комментарий
  в успешном запросе не передавались; кухня не проверена.
- SumUp Get Merchant подтвердил IE/EUR sandbox. Создание Hosted Checkout
  подтверждено ответами `201` с исходным статусом `PENDING`.
- После более ранней незавершённой попытки был зафиксирован один успешный
  100-cent SumUp sandbox flow: реальный webhook, server-side verification,
  checkout `PAID`, ровно одна `SUCCESSFUL` transaction, atomic local `paid` и
  duplicate replay без повторной верификации или изменения состояния.

Это история проверок, а не подтверждение актуальности доступов сегодня.
Подробности и коммиты сохранены в `docs/CHANGELOG.md`.

### Всё ещё не подтверждено

Этот успешный SumUp flow является историческим доказательством, а не
подтверждением нового текущего запуска или актуальности доступа. Точное
сохранение Poster prepayment и остальных полей, появление заказа у кухни и
полный сквозной сценарий до Poster остаются неподтверждёнными. Причины более
раннего отсутствия webhook и Poster `422` неизвестны.

Provider-neutral orchestration boundary и локальный provider-specific OpenAI
adapter с HTTP transport для команд уже реализованы; controlled runtime
connection, реальная свободная языковая семантика, социальные каналы, передача
сотруднику и полноценный журнал событий ещё не реализованы.
Проект не готов к пилоту.

## Границы проекта и существующий сайт

**ChoiceQR не является частью основной архитектуры проекта.** Существующий сайт Sushi Planet продолжает работать через ChoiceQR независимо от нашего агента.

ChoiceQR остаётся на паузе как возможная вспомогательная интеграция. Если прямое
подключение к Poster окажется неудобным, его роль можно рассмотреть отдельно;
возвращение ChoiceQR в scope требует явного решения пользователя.

В первой версии мы:

- не перестраиваем сайт;
- не меняем его навигацию;
- не меняем его оформление;
- не заменяем ChoiceQR;
- не создаём новый сайт вместо существующего.

Основная задача проекта — добавить автоматическое оформление заказов через социальные сети и передачу оплаченных заказов в Poster.

В будущем при необходимости можно добавить чат-виджет на существующий сайт, CRM, аналитику и другие интеграции. Это отдельные этапы и не входит в обязательный объём первой версии.

## Рабочее архитектурное решение

Мы строим собственный слой агента и логики заказа.

Мы не создаём заново:

- POS-систему;
- платёжную систему;
- сайт;
- языковую модель;
- полноценную CRM на первом этапе.

Целевая схема (сквозной сценарий ещё не реализован и не проверен):

```text
Каналы общения
→ адаптеры Instagram / WhatsApp / Facebook / Telegram
→ provider-neutral AI interpreter
→ единый сервер агента
→ меню, корзина, доставка и заказ
→ один выбранный платёжный сервис (первый кандидат — SumUp)
→ подтверждённая оплата
→ Poster API
```

ChoiceQR поставлен на паузу и возвращается только отдельным явным решением
пользователя. Платёжный сервис должен выбираться
отдельно от существующего Adyen-потока сайта; первая проверяемая кандидатура —
SumUp sandbox.

Poster должен быть источником правды для:

- заказов;
- блюд и их идентификаторов;
- кухни;
- статусов заказа;
- базовых данных клиента.

Наша собственная база нужна для:

- связи клиента с аккаунтом Instagram, WhatsApp, Facebook или Telegram;
- истории диалога;
- связи заказа с платежом;
- защиты от повторного создания заказа;
- технических логов;
- статуса передачи заказа.

ChoiceQR остаётся независимым существующим каналом сайта. Его CRM и онлайн-заказы не являются обязательной частью первой версии агента.

## Целевой сценарий заказа

1. Клиент пишет в соцсеть.
2. Агент отвечает и помогает выбрать блюда.
3. Агент получает имя, телефон, адрес и время доставки.
4. Система проверяет меню, цены, доступность и правила доставки.
5. Создаётся заказ со статусом `Ожидает оплаты`.
6. Клиент получает ссылку на оплату.
7. Платёжный сервис отправляет подтверждение об успешной оплате.
8. Система создаёт оплаченный онлайн-заказ в Poster.
9. Poster показывает заказ сотрудникам и кухне.
10. Агент сообщает клиенту, что заказ подтверждён.
11. При изменении статуса агент отправляет клиенту обновление.
12. Если вопрос сложный, диалог передаётся сотруднику.

## Что нельзя допускать

- Агент не должен придумывать блюда, цены, наличие или время доставки.
- Все суммы должны рассчитываться системой, а не только языковой моделью.
- Нельзя считать сообщение клиента «я оплатил» доказательством оплаты.
- Только подтверждение от платёжного сервиса меняет статус на оплаченный.
- Один заказ нельзя отправить в Poster дважды.
- Нельзя хранить данные банковских карт.
- Нельзя отправлять реальные заказы в производство до тестирования.
- Нельзя делать массовый рефакторинг и добавлять функции вне согласованного объёма.
- Нельзя менять существующий сайт без отдельного согласования.

## Что ещё нужно получить

Для реального подключения понадобятся:

- завершение проверки оплаченного заказа через Poster API, его полей и кухни;
- подтверждение актуальности ранее проверенного SumUp sandbox-доступа перед
  следующей отдельно разрешённой внешней проверкой;
- повторная актуальная проверка исторически успешного SumUp sandbox flow перед
  пилотом;
- отдельный доступ к реальному Poster Sushi Planet от Александра или владельца
  аккаунта перед production-подключением;
- доступ к Meta Business с нужными разрешениями;
- подтверждение, какие каналы запускаются первыми;
- данные по доставке, минимальной сумме и времени приготовления.

Пароли не хранить в репозитории. Использовать `.env`, Keychain или другой безопасный способ хранения секретов.

## Первая версия

Первая версия должна включать:

- один основной канал для пилота;
- меню и корзину;
- расчёт итоговой суммы;
- адрес и тип заказа;
- оплату;
- подтверждение платежа;
- создание заказа в Poster;
- сообщение клиенту;
- передачу диалога сотруднику;
- обработку ошибок и отмены;
- журнал событий.

Не включать в первую версию:

- полноценную CRM;
- сложную программу лояльности;
- массовые рекламные рассылки;
- автоматическую работу всех каналов одновременно;
- замену ChoiceQR или Poster;
- собственную систему доставки;
- новый сайт;
- хранение карточных данных.

## Критерии готовности

Система считается готовой к пилоту, если:

- правильное блюдо попадает в Poster;
- количество, модификаторы и цена передаются правильно;
- адрес и телефон передаются правильно;
- успешная оплата подтверждается автоматически;
- один заказ создаётся только один раз;
- кухня видит заказ в Poster;
- клиент получает подтверждение;
- ошибка оплаты не создаёт оплаченный заказ;
- сотрудник может перехватить диалог;
- все ключевые события записываются в журнал.

## Правила работы над проектом

Перед каждой работой:

1. Прочитать `AGENTS.md`, этот README и `PLAN.md` в указанном порядке.
2. Проверить текущее состояние проекта.
3. Чётко определить задачу текущей сессии.
4. Не менять несвязанные части проекта.
5. Отмечать неподтверждённые предположения.
6. Подробные завершённые изменения записывать в `docs/CHANGELOG.md`; этот README
   менять только при ключевом изменении проекта или завершении крупного этапа.
7. Не подключать реальные платежи и production-аккаунты без отдельной проверки.
8. Не менять существующий сайт без отдельного согласования.

Текущая стратегия: завершить основу агента и проверки Poster на отдельном
тестовом аккаунте и SumUp sandbox, затем переходить к социальным каналам.
Работы по Poster и SumUp уже частично пересекались; это не означает завершения
этих этапов. Смена платёжного сервиса требует отдельного решения. Готовые
платформы вроде Moon AI можно сравнить позже, если они дадут необходимые
интеграции.

Подробная техническая история проекта находится в `docs/CHANGELOG.md`.
